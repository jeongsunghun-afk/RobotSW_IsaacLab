## 0. 규약 정의

`convention_version` 은 **"송신자가 실제로 무엇을 하는가"** 를 가리킨다.
"무엇이 판정됐는가"가 **아니다** — 그러면 수신측이 패킷만 보고 바이트 해석을 결정할 수 없어
와이어 프로토콜 버전으로서 쓸모가 없어진다.

| 값 | 의미 |
|---|---|
| **0** | gear 미적용 + foot **raw**각(`q_foot + q_calf`). 필드가 없는 84 B STATE / 120 B TELEM 이 곧 버전 0 |
| **1** | gear 적용(위치·속도) + foot **관절**각. `tau` 는 변환 없이 통과(채널기준) |

- sim 에는 gear 개념이 없다(채널각 자체가 없다) → **좌표 의미로만** 판정한다.
- 버전을 올려야 하는 변경: 송신자가 좌표·단위 변환을 **추가하거나 제거**했을 때.
  무언가 *판정*만 된 것은 버전 변경 사유가 아니다.

정본 정의: `real_runner/r2s_packets.hpp` 의 `R2S_CONVENTION_VERSION`.

### B4 — policy 모드 커플링 (2026-08-14 착지)

`_apply_action` (`r2s_biped_leg_env.py:570`) 의 policy 분기 (`:575`):
```python
raw_t = self._policy_target[:, self._foot_art_ids] + self._policy_target[:, self._calf_art_ids]
```
**목표값끼리** 합성한다 — 학습 env `hind_leg_env.py:267`
(`raw_t = processed_actions[foot] + processed_actions[calf]`) 와 **같은 식**이라, 배포 리허설이
학습과 일치한다. `_pre_physics_step` (`:316`) 의 policy 분기 (`:317`) 는 관절 목표를 그대로 넣고
raw 합성은 `_apply_action` 에 맡긴다.

**해소 전 상태 (기록)** — 2026-08-14 11:28 이전에는 policy 모드가 커플링을 **통째로 건너뛰어**
foot 이 독립 관절로 구동됐다. 학습 env 는 커플링을 적용하는데 **배포 리허설만 안 하는** 상태였다.
즉 그때까지 sim 에서 한 정책 테스트는 학습 때 거동과 달랐다.

### ★B3/B5 — 한때 서로 반대였던 두 메서드 (해소, 교훈은 유지)

**현재는 둘 다 관절 좌표다.** `get_lowstate` 의 raw 합산이 제거됐다(`:159` docstring 참조 —
"밖으로 나가는 값은 전부 관절각"). 그래도 이 항목을 남기는 이유는 아래 사고 때문이다.

2026-08-14 이전, r2s env 에는 **커플링 처리가 반대인 상태 반환 메서드가 두 개** 있었다:

| 메서드 | 그때 foot 좌표 | 쓰는 곳 |
|---|---|---|
| `get_lowstate` | **raw** (`foot_coupling` 이면 `q_foot + q_calf` 합산) | GUI 슬라이더/monitor |
| `get_policy_state` | **관절** (`robot.data.joint_pos` 그대로) | `sim_runner` STATE |

`sim_runner_bipedleg.py:308` 이 쓰는 건 **`get_policy_state`** 다.

team lead 가 `get_lowstate` 를 보고 "sim 은 규약 0" 이라 판단해 sim 이 `0` 을 신고하도록 지시했다.
**틀린 지시였다** — sim STATE 는 이미 관절이라 0 은 거짓 신고가 되고, "버전 0 거부" 규칙과
합쳐지면 좌표가 멀쩡한 sim 을 이유 없이 차단한다. 정정 후 **sim STATE 는 1 로 신고**한다.

⇒ **같은 데이터의 반환 경로가 여러 개면 메서드 이름까지 확인할 것.** "sim 은 raw/관절" 로만
말하면 또 틀린다. 지금은 둘이 같아졌지만, 경로가 갈라지는 순간 이 함정이 되살아난다.

## C. 버전 신고 정직성

- **C1** 각 송신자(브리지 real · `sim_runner`)가 **자기 동작과 일치하는** 값을 보내는가.
  좋아 보이는 값이 아니라 **실제로 하는 일**을 신고해야 한다.
- **C2** 소비자(`policy_runner` · GUI · `comm_check`)가 **모르는 버전을 거부**하는가.
  조용히 받아들이면 이 체계 전체가 무의미해진다.
- **C3** 거부 메시지가 원인을 지목하는가 — 예: `규약 불일치: 수신 0, 기대 1`.
- **C4** 게이트가 필요하면 **버전을 거짓말시키지 말고 명시적 게이트**를 둘 것.
  의도가 코드에 드러나야 한다.

## E. 수치 검증

- **E1 왕복** — 관절 목표 → 채널 → 관절 이 항등인가.
  **`calf ≠ 0` · `foot ≠ 0` · 좌우 비대칭** 입력 필수: calf 가 0 이면 커플링이 안 드러나고,
  좌우 대칭이면 좌우 혼선을 못 잡는다. 기준 위치 < 1e-6 rad, 속도 < 1e-6 rad/s.
- **E2 커플링 발현** — foot 채널 / calf 채널 비가 `gear_f / gear_c` 예측과 맞는가
  (RL_INTERFACE §2-a 의 `k_foot/k_calf = 1.2/1.5 = 0.8` 관계).
- **E3 sim↔real 동형** — 같은 관절 목표 벡터를 양쪽에 주입 → 되읽은 관절각 일치.
  B4(policy 모드 커플링)가 2026-08-14 착지해 **동적 비교도 유의미해졌다.**
  ⚠ 그래도 정적 일치만 보고 통과시키지 말 것 — §F4 의 원칙(좌표 일치 ≠ 플랜트 일치)은 유효하다.
- **E4 ±180 여유** — 관절 한계 극단 조합의 채널각. 현재 160.096°(여유 19.9°).
  ★`zero_deg` 캘리브레이션이 들어가면 수십 도 offset 이 더해져 이 여유가 사라진다.
  드라이버는 클램프가 아니라 **래핑**하므로(§5) 반대편으로 날아간다 — **영점 작업 후 반드시 재확인.**

검산 하네스는 **실제 소스에서 변환 함수를 `sed` 로 추출해** 실제 헤더와 함께 컴파일하는 방식으로
쓸 것. 손으로 옮겨 적으면 코드와 검산이 갈려서 검산이 무의미해진다.

## F. 판정 규칙

1. **A 전항 통과 없이 B~E 판정 금지.** 크기가 틀리면 데이터가 아예 안 오므로 이후 항목이

3. **같은 데이터의 반환 경로가 여러 개면 메서드 이름까지 적어 확인한다.**
   "sim 은 관절" 같은 요약이 실제로 오판을 낳았다(§B3/B5).
4. ~~**B4(커플링 물리 부재)가 남아 있는 동안 E3 를 통과로 판정하지 않는다.**~~
   → **2026-08-14 해소** (policy 모드 커플링 착지). 조건은 풀렸지만 **원칙은 남긴다**:
   **좌표 일치와 플랜트 일치는 별개 항목이다.** 좌표계가 맞아도 동역학이 다르면 E3 는 정적으로만
   통과한다. 다음에 비슷한 이관을 할 때 이 구분을 다시 세울 것.
5. **한 지점이라도 규약이 다르면 전체 FAIL.** 부분 통과는 의미가 없다 —
   조용히 어긋나는 것이 이 작업의 유일한 실패 모드이므로, "대부분 맞다"는 상태가 가장 위험하다.
6. ★**문서의 코드 서술은 mtime 과 무관하게 코드로 재검증한다.**
   문서가 최근에 갱신됐다는 사실은 그 안의 **코드 서술이 최신이라는 근거가 되지 않는다.**
   갱신할 때 건드린 절만 최신이 되고 나머지는 그대로 낡기 때문이다.

   > **실제 사례** — 이 문서의 §B4 가 그랬다. `r2s_biped_leg_env.py` 는 11:28 에 policy 모드
   > 커플링이 착지했는데, 이 문서는 12:07 에 **더 나중에** 갱신됐음에도 §B4 는 "커플링 물리 없음"

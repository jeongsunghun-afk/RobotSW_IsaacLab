# RSI 클립을 명령 속도에 맞춰 뽑기 — 속도-보행 전환이 생기는가 (2026-08-28~)

## 질문

[`gait_attractor_pace_vs_gallop`](../gait_attractor_pace_vs_gallop/README.md) 에서 확인한 것:
정책은 속도가 올라도 걸음을 안 바꾼다. 참조에는 사다리(walk <1 / pace 1.97 / gallop 2.69~3.03)가
있는데도 4.0 까지 pace 로 간다. 원인 후보는 **RSI 클립과 명령이 독립적으로 뽑힌다**는 것 —
gallop 자세로 시작했는데 명령이 0.5 이거나 walk 자세인데 3.2 인 조합이 생겨, 걸음이 명령과
결합되지 못하고 자유 변수로 남는다.

처방: RSI 에서 명령을 먼저 뽑고 **그 속도에 가까운 클립**을 고른다(`rsi_match_command`).

## 상태: 종결 — rsimatch 50k 완주, **처방 기각**(초기화 artifact). 후속 A/B(`cmdchg`) 착수

## 판정 기준을 먼저 못박는다

baseline 의 gallop 은 **속도와 무관하게 고르게** 퍼져 있다(1.5~2.5 에서 20%, 2.5~3.5 에서 23%).
따라서 **총 gallop% 가 오르는 것은 성공 신호가 아니다** — 그건 같은 무작위 gallop 을 더 많이
내는 것일 뿐이다. 처방이 통했다는 신호는 **속도축에서 단조 증가하는 모양**, 즉 참조 gallop
속도(2.69 m/s) 위에서만 gallop 이 나오는 것이다.

## ① baseline 의 gallop 발현 곡선 — 20k 이전엔 비교 자체가 불가능

10k 만 보고 판정하려던 것을 막아 준 대조. 같은 run 의 체크포인트만 바꿔 쟀다(RSI 출발, 4096 env):

| baseline 체크포인트 | 전체 gallop% | cmd 1.5~2.5 | cmd 2.5~3.5 |
|---|---|---|---|
| model_10000 | **0.4%** | 0.0 | 0.0 |
| model_20000 | 17.8% | 20.0 | 23.1 |
| model_30000 | 19.6% | 21.2 | 24.8 |
| model_40000 | 20.3% | 23.7 | 22.2 |
| model_49999 | 19.9% | 24.1 | 21.8 |

**gallop 은 10k~20k 사이에 갑자기 나타나고 그 뒤로는 평평하다.** 10k 체크포인트끼리의 비교
(baseline 0.4% vs rsimatch 0.6%)는 양쪽 다 바닥이라 아무 정보가 없었다.

⚠️ 이 발현은 **속도가 붙어서가 아니다**. cmd 2.5~3.5 에서 실제 낸 속도는 10k 에 2.67,
50k 에 2.73 으로 사실상 같다. 속도는 10k 에 이미 다 올라와 있고 걸음만 나중에 갈라진다.

## ② 20k 짝맞춤 — 모양이 갈린다

| cmd vx | baseline@20k gallop% | rsimatch@20k gallop% |
|---|---|---|
| 0.5~1.5 | 1.0 | 3.5 |
| 1.5~2.5 | **20.0** | **2.0** |
| 2.5~3.5 | **23.1** | **14.0** |
| 전체 | 17.8 | 6.1 |

- baseline: 20.0 → 23.1, **평평**(속도와 무관)
- rsimatch: 2.0 → 14.0, **7배 단조 증가**

gallop 표본의 명령속도 중앙값도 baseline 2.36 → rsimatch **2.67** 로 올라간다. 참조상 gallop
속도대(2.69~3.03)의 문턱이다.

총 gallop% 는 오히려 낮은데(6.1 vs 17.8), 위 기준대로면 이건 **저속의 무작위 gallop 이 걷힌
것**으로 읽힌다. n 이 847~1329 이라 2.0% vs 20.0% 는 잡음 범위가 아니다.

20k 한 점만으로는 이것이 (a) 진짜 속도 선택성인지 (b) 단순히 발현이 늦어진 것인지 가를 수
없었다. (a) 라면 고속 칸만 계속 오르고 중속 칸은 낮게 남고, (b) 라면 중속 칸이 따라 오른다.

## ③ 30k — **(a) 로 갈렸다**

| cmd vx | baseline@30k | rsimatch@20k | **rsimatch@30k** |
|---|---|---|---|
| 0.5~1.5 | 5.6 | 3.5 | 7.7 |
| 1.5~2.5 | **21.2** | 2.0 | **6.4** |
| 2.5~3.5 | **24.8** | 14.0 | **68.2** |
| 전체 | 19.6 | 6.1 | 26.2 |

고속 칸만 14.0 → **68.2** 로 뛰었고 중속 칸은 2.0 → 6.4 에 머물렀다. 고속/중속 비율 **10.7 배**
(baseline 은 1.2 배). 발현 지연 (b) 는 아니다.

gallop 표본의 명령속도 중앙값 2.81 m/s — 참조 gallop 대역(2.69~3.03) 한가운데다.
선회를 갈라 봐도 직진 칸이 가장 높다: cmd 2.5~3.5 에서 `|yaw|<0.5` 73%, 좌우 선회 61/70%.

끝까지 이어진다 — cmd 2.5~3.5 / cmd 1.5~2.5 의 gallop%:
20k 14.0/2.0 → 30k **68.2**/6.4 → 40k **72.7**/11.5 → 50k **66.7**/12.4.

### ⚠️ 그러나 (c) 가 남는다 — 그리고 ④⑤ 를 보면 (c) 가 맞다

같은 격자를 내는 세 번째 설명이 있다:

> **(c) 걸음은 여전히 초기 자세가 잠그는데, 그 초기 자세가 이제 명령과 상관된다.**

이건 변방 가설이 아니라 우리가 바꾼 것의 **기계적 귀결**이다. 매칭을 켜면 `leg_run` 프레임에서
출발한 env 는 **항상** 고속 명령을 받으므로, "gallop 자세 + 고속" 만 보고 "gallop 자세 + 저속" 은
아예 안 본다. 전환 능력이 0 이어도 격자의 상관은 그대로 올라간다.

정지 출발 램프가 (c) 의 첫 증거다 — cmd 1.5/2.0/2.5/3.0 전부 pace, 바뀌는 건 주파수뿐
(1.73 → 2.28 Hz). (a) 는 격자만 설명하지만 (c) 는 격자와 램프를 **동시에** 설명한다.

## ④ ★★★ 애초에 전환을 배울 신호가 없다 — `_post_physics_step` 이 호출되지 않는다

(a)/(c) 를 가르려고 "에피소드 도중 명령이 바뀌는 순간"의 앞뒤 걸음을 비교하려 했다. 그런데
4096 env 8 s 조사에서 **명령 변경이 일어난 env 가 4091 개 중 0 개**였다(`tar_change_time`
4~7 s 설정이면 전부 한 번씩 바뀌어야 한다).

원인:

```python
# leg_imitation_tracking_env.py:206
def _post_physics_step(self):
    self._tar_timer -= self.step_dt        # ← 이 메서드는 아무도 부르지 않는다
    ...
        self._resample_steering(change_ids)
```

`DirectRLEnv.step()` 에 `_post_physics_step` 훅이 **없다**(`_pre_physics_step` / `_apply_action` /
`_get_dones` / `_get_rewards` / `_reset_idx` / `_get_observations` 뿐). `source/isaaclab/` 전체와
이 env 안 어디에서도 호출되지 않는다. 즉:

- `tar_change_time_min/max` 는 **죽은 설정**이다.
- 명령은 **리셋 때 한 번 뽑혀 에피소드 내내 고정**된다.
- 정책은 "달리는 중에 명령이 바뀌는" 상황을 **한 번도 겪은 적이 없다.**

같은 죽은 메서드가 `go2_imitation_tracking_env.py:299` 에도 있다 — 계보 전체의 문제다.

→ 속도-보행 전환이 안 생기는 진짜 이유는 최적화 우물도, RSI 독립성도 아니라 **전환을 학습할
신호 자체가 없다**는 것이다. RSI 매칭은 초기화를 조건화할 뿐이라 이 결핍을 못 메운다.
(기각) 이전에 이 문서와 대화에서 "명령이 4~7 초마다 바뀌므로 전환 기회가 학습 중에 생긴다"고
적은 것은 **틀렸다.**

## 명령 분포 왜곡 방지 — 설계와 검증

가장 큰 위험은 "명령 분포가 데이터 쪽으로 끌려가는 것"이다. 명령 샘플링(`_resample_steering`)은
한 줄도 안 건드렸고 **초기 자세 선택만** 바꿨다. 하드 최근접이 아니라 softmax(τ=0.5)를 쓰고,
기존 `_motion_weights`(=`command_uniform`)를 곱해 클립 주변분포를 보존한다.

20만 표본 검증:

| 항목 | 결과 |
|---|---|
| 명령 분포 | mean 1.5993 / std 0.9246 (기대 1.6000 / 0.9238) — 불변 |
| 클립 사용 주변분포 | 최다 클립 20.09% → 21.54%, 나머지 ±1%p 이내 |
| 조건부 (클립 \| 명령) | cmd [0,0.5)→0.57 m/s, cmd [2.3,3.2)→**2.52** (기존 둘 다 1.59) |
| mirror 쌍 균형 | 최대 편차 0.06%p |

## 결론

처방 `rsi_match_command` 는 **의도한 것을 하지 않는다**. 속도-보행 사다리가 안 생기는 이유는
RSI 와 명령이 독립이라서가 아니라, ④ 대로 **에피소드 중 명령이 바뀌지 않아 전환을 학습할 신호가
아예 없기** 때문이다. 초기화를 조건화하는 어떤 변형도 이 결핍을 메울 수 없다.

다음 지렛대는 매칭 온도가 아니라 **명령 동역학**이다. → 후속: `cmdchg` A/B (아래)

## ⑥ 후속 A/B — 명령 재샘플링을 되살렸다 (`cmdchg`, 진행 중)

`_post_physics_step` 을 `_resample_steering_on_timer()` 로 고쳐 살아 있는 훅
(`_get_rewards()` 끝)에서 호출하고, `resample_command_in_episode`(기본 False)로 게이트했다.
`_get_dones()` 가 아니라 `_get_rewards()` 끝인 이유: 그 step 의 보상은 **옛 명령**으로 계산되고
이어지는 관측이 **새 명령**을 실어야 한다. 기본 False 인 이유: 지금까지의 모든 run 이
"명령 고정" 조건에서 학습됐고, 기본값을 뒤집으면 그 결과들의 의미가 조용히 달라진다.

동작 검증(플래그 ON, 2048 env·10 s): **2048/2048 env 가 재샘플링**하고, 에피소드 리셋을 제외한
순수 재샘플 간격이 **3.98~7.84 s**(설정 4~7 s)로 나온다.

- 새 팔: `2026-09-01_09-04-53_cmdchg_velscale15_ds14_wcmd_vmax32`
- 대조: 기존 `2026-08-26_16-51-43_velscale15_ds14_wcmd_vmax32`
- cfg 대조 결과 실질 차이는 **`resample_command_in_episode: true` 하나**
  (`rsi_match_command: false` 는 신규 키의 기본값이라 동작 변화 없음)

★ 이 변경은 학습 env 의 명령 동역학을 바꾸므로 **기존 판정 전체의 조건이 달라진다**
(`vel_err_scale` 판정 포함 — 그 실험들도 전부 "명령 고정" 조건에서 잰 것이다).

판정 방법: `gait_transition_probe.py` 가 이제 표본을 얻는다 — 명령이 저속→고속으로 바뀐 env 에서
걸음이 pace→gallop 으로 따라 바뀌는 비율. 이번 팔에서 이 값이 오르면 **전환이 실재**하는 것이고,
그때 비로소 정지 출발 램프에서도 사다리가 나와야 한다.

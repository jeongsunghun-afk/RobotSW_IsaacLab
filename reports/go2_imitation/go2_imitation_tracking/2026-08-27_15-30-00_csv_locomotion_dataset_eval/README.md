## 1. 이게 무엇인가

- **형식**: CSV, 컬럼 `frame,joint_idx,x,y,z,base_rel_*,base_frame_*,roll,pitch,yaw,linear_vel_*,angular_vel_*`. 파일당 `joint_idx` 0~26 (27개 keypoint) × frame 수 만큼 row.
- **좌표계**: `mujoco_retarget_go2/stmr_go2.py:load_motion_data` 주석 확정 — **CSV(X=fwd, Y=up, Z=right)**, 단위 m, rad.
- **fps**: `stmr_go2.py --dt` 기본값 `0.01667` → **60fps** (파일명 `F630_F830`의 프레임 범위와도 일치).
- **골격**: `REF_JOINT_MAP`(`stmr_go2.py:33`)에서 `PELVIS=0`, `NECK=24`, `HIP/KNEE/ANKLE/TOE` 등 27관절 매핑 확인 — **원본 개 mocap 키포인트**이지 이미 로봇으로 리타게팅된 게 아니다.
- **파이프라인 위치**: 이 csv는 `stmr_go2.py --data_path <dir>` 의 **입력**이다(디폴트 `csv_dataset_small`과 동일 스키마). SMR(공간)+TMR(시간) 을 거쳐 `.txt`(DeepMimic 61-D) → `convert_smr_to_pkl.py` 로 `frames(N,18)` PKL 이 나온다. 즉 저장소가 쓰는 PKL 로부터 **두 단계 앞**의 원자재다.
- **⚠ 함정(사전 확인 안 하면 결과가 깨짐)**: csv 자체에 `linear_vel_x`/`angular_vel_yaw` 컬럼이 있지만 **raw 미분값이라 yaw 랩(gimbal-lock 포함) 스파이크가 그대로 들어있다**(예: `spin` 클립에서 `angular_vel_yaw` ±376 rad/s). 이 분석은 그 컬럼을 버리고 `roll/pitch/yaw`에서 직접 `np.unwrap`+`np.gradient`로 재계산했다.

## 2. Go2 PKL까지의 경로와 비용 (실측)

| 단계 | 스크립트 | 상태 |
|---|---|---|
| CSV → SMR(공간 리타게팅) → TMR(시간축 최적화) → `.txt` | `mujoco_retarget_go2/stmr_go2.py` | **이미 존재, 그대로 사용 가능** |
| `.txt` → `frames(N,18)` PKL | `mujoco_retarget_go2/convert_smr_to_pkl.py` | **이미 존재** (순수 numpy, 비용 무시 가능) |
| 좌우 미러 증강 | `stmr_go2.py --mirror` | **이미 존재** — 원본 그대로 대신 `--mirror` 플래그로 대체 가능(§5 참고) |

**새로 짤 코드 없음.** 실측(conda env `stmr`, `mujoco==3.4.0`, CPU): 5개 walk 클립(199/281/315/19/36 프레임) 전체 SMR+TMR 처리 **24.7초**(프로세스 시작 오버헤드 포함), 클립당 평균 **~4.9초**. 이를 외삽하면:

| 처리 대상 | 클립 수 | 예상 시간(단일 프로세스) |
|---|---|---|
| 전체 1,676개 그대로 | 1,676 | **~2.3시간** |
| 미러 제외 고유 838개 + `--mirror` 플래그로 재생성 | 838 | **~1.1시간** (§5 근거로 권장) |

8-core 병렬화 시 각각 ~17분/~8분으로 단축 가능(임베러싱리 패러렐, 클립 간 의존성 없음).

TMR은 시간축 alpha를 최적화하며 실측 클립당 alpha=1.17~1.89(로봇이 개보다 느리게 재생) → 출력 프레임 수는 입력의 alpha배 (`199→312`, `36→67` 등 실측 확인). 즉 최종 PKL 프레임 수는 raw 프레임 수보다 **오히려 늘어난다.**

† `wz` min/max는 gimbal-lock(피치 ±90° 근접 시 Euler yaw 불연속, 전체 프레임의 **0.67%**만 영향) 포함 raw 값. **percentile(p5~p95)로 보면 각 카테고리 wz는 -7.4~7.5 rad/s 이내로 정상 범위** (상세는 `metrics/loco_csv_stats.json`).

- **후진 클립 존재 여부 → 예, 확실히 존재한다.** `walk`(16.0%), `spin`(39.2%), `walk_sit`(34.9%), `walk_stand`(25.8%) 전부 `v_x<0` 프레임을 상당량 포함. 현행 PKL(0% 후진)과 대비되는 가장 큰 개선점.
- **`spin`(38클립)이 고yaw를 채우는가 → 예**, p95 wz=7.47 rad/s로 task 상한(1.5)의 5배. 단 spin의 전진속도는 거의 0(제자리 회전)이라 "고속+고yaw" 조합에는 기여하지 않는다.
- **고속(v_x>1)×고yaw(|wz|>1) 조합 → 현행 데이터의 최대 구멍이었는데, 여기선 `run`에서 프레임의 53.5%가 이 조건을 만족한다.** 달리면서 도는 개 mocap이 실제로 존재함 — 이전 8클립 PKL엔 이 조합이 전무했다.

### 2D 커버리지 그리드 (`v_x∈[-1,3]` 8bin × `yaw∈[-1.5,1.5]` 6bin = 48칸)

| | 스케일 보정 없음 | Walk-Like-Dogs α 적용(α_fwd=0.6, α_yaw=1.0) |
|---|---|---|
| 전 카테고리(1,676클립) | **48/48 (100%)** | **48/48 (100%)** |
| walk/run/trot/spin만(전이 제외) | 48/48 (100%) | 48/48 (100%) |
| gimbal-lock 프레임(0.67%) 제거 후 | 48/48 (100%) | 48/48 (100%) |

현행 41.7%(20/48) 대비 **+58.3%p**. 가장 성긴 칸도 프레임 14개 이상 확보(스케일 적용 후 최소칸).

### ⚠ 중요한 caveat — 이 숫자는 "리타게팅 전" 근사치다

여기서 쓴 α_fwd=0.6는 논문의 **개→로봇 신체 스케일 보정**이다. 반면 §2에서 실측한 TMR alpha(1.17~1.89)는 **로봇 동역학 제약에 의한 시간축 재조정**으로, 최종 속도를 `raw_v / TMR_alpha`만큼 한 번 더 낮춘다(같은 거리를 더 긴 시간에 이동). 두 보정을 합치면 `v_fwd_scaled × 0.6 / 1.5(대표 alpha) ≈ raw × 0.4` 수준까지 내려갈 수 있다. 이 보고서는 TMR 이후 실측치가 아니라 **원본 csv만으로 계산한 근사값**이므로, 100% 커버리지는 "raw 데이터에 정보가 존재한다"는 뜻이지 "리타게팅된 PKL이 정확히 이 분포를 갖는다"는 보장은 아니다. **본격 착수 전 대표 클립 50~100개를 실제로 리타게팅해 사후 v_x/wz를 재검증할 것을 권고.**

## 4. 보행 무관(전이) 카테고리 판별

높이(up=y) 궤적 직접 확인:

- **`walk_sit`**: 0.123m(앉음) → 0.51m(보행 높이)로 상승 — **앉음→기립→보행 전이**.
- **`walk_stand`**: 0.46~0.48m로 큰 변화 없음 — 서있는 자세의 미세 조정, sit만큼 극적이지 않음.
- **`run_walk` / `walk_run`**: 높이 0.39~0.52m 사이 변동 — **gait 전환(달리기↔걷기)**, 자세 전이 아님.

**권고: latent VAE 학습에 포함(배제하지 말 것).** 상태전이 데이터가 희소한 것이 baseline 8클립 PKL의 문제 중 하나였고(latent_imitation_plan 보고서, "상태전이 2,214쌍뿐"), 이 4개 카테고리(96클립, 18,250프레임)가 정확히 "모드 간 전이" 학습 신호를 채워준다. 단, `walk_sit`/`walk_stand`는 정적 자세(낮은 속도)라 command-conditioned 학습에선 별도 태그(예: `is_transition=1`)로 구분해 tracking reward에서 과도한 speed-tracking 페널티를 받지 않게 할 것을 권고.

## 5. 품질

- **NaN**: 0/1,676 파일에서 검출 안 됨.
- **프레임드롭**: 검출 안 됨(파일별 frame index가 0..N-1 연속, gap 없음 — 27개 joint × N frame 행 수가 정확히 일치).
- **길이 분포**: 평균 2.82s, 중앙값 2.74s, **최소 0.32s, 최대 9.98s**. `duration<1.0s` 클립이 **462/1,676(27.6%)**, `<0.5s`가 248개(14.8%) — BC/VAE 학습엔 노이즈에 가까운 초단클립 비중이 상당히 큼.
- **★★ 중복 구조(핵심 발견)**:
  1. **파일명 `M_` 접두사 = 좌우 미러 클립.** 전 카테고리에서 정확히 **50.0%**(838/1,676)가 `M_` 파일이고, 원본과 `x`(전진), `y`(높이) 좌표가 **완전히 동일**, `z`(측면)만 부호 반전 확인. 즉 **고유 원본 클립은 838개**, 나머지 절반은 사전 생성된 미러 증강이다.
  2. **슬라이딩 윈도우 과분절.** 파일명 패턴 `<subj>_<sess>_<take>_F<start>_F<end>_<idx>`을 파싱해 (subj,sess,take) 단위로 묶으면, 1,676개 클립 배후의 **원 녹화 세션은 46개뿐**(walk 34, run 12, trot 6, spin 3, walk_sit 6, walk_stand 8, run_walk 4, walk_run 1)이며, 대부분 겹치는 프레임 구간(`F138_F166`, `F138_F189`, `F166_F189`…)을 촘촘히 슬라이딩 윈도우로 잘라 클립 수를 부풀린 것이다. 46개 세션의 **합집합 raw 구간은 총 97,320 프레임(≈27분)** — 이것이 진짜 독립적인 mocap 정보량의 상한이다.
  3. **피험견(subj 토큰) 다양성은 확보**: `D1_001~D1_073`, `D1_exXX` 등 **28개 서로 다른 subj 토큰**이 전 카테고리에 분포 — 세션 수는 적어도 견종/개체 다양성 자체는 있음.
- **결론**: 1,676이라는 클립 수는 **표면적 숫자**이고, 실제 정보량은 (a) 미러로 ½, (b) 슬라이딩 윈도우 중복으로 다시 상당히 줄어 **~46개 세션·약 27분**이 진짜 상한이다. 그럼에도 27분은 현재 PKL의 18.6초보다 **~87배** 길고, 프레임 목표(10,000)를 가볍게 넘긴다(27분×60fps=97,200 raw frame).

## 6. 최종 판정 및 권고

**Green — 목표(프레임≥10,000, 커버리지≥70%)를 raw 단계에서 이미 초과 달성.** 단 §3 caveat(TMR alpha로 인한 속도 재조정)로 인해 **전량 리타게팅 후 재검증 필수**.

### 구체 권고
1. **리타게팅 대상**: `M_` 접두사(미러) 838개는 건너뛰고, **고유 838개**에 `stmr_go2.py --mirror`를 적용 — 결과는 동일(원본이 이미 좌우대칭 쌍이므로)하되 계산량 절반(§2).
2. **카테고리 전량 사용 권장**: `walk`(1,316→미러제외 658)를 중심으로 `run`(81)·`trot`(45)·`spin`(19)·전이 4종(48)까지 전부 포함 — 고속×고yaw 공백을 메우는 `run`, 고yaw를 메우는 `spin`, 전이 신호를 메우는 `walk_sit/stand/run_walk/walk_run`을 절대 빼지 말 것(§3, §4).
3. **초단 클립 필터링 고려**: `duration<0.5s`(248개, 미러 포함이므로 고유 기준 ~124개) 클립은 VAE 상태전이 학습(20 epoch)엔 문제 없으나 autoregressive 학습(60 epoch)에는 노이즈가 될 수 있어, 최소 프레임 수 컷(예: ≥30프레임/0.5s) 적용을 권고.
4. **본 착수 전 검증 스텝**: 대표 50~100클립(속도·yaw 전 구간에서 층화 샘플)만 먼저 실제 STMR 리타게팅 → 실측 `v_x, wz` 재계산 → 이 보고서의 100% 커버리지가 TMR alpha 적용 후에도 유지되는지(특히 `run` 카테고리의 고속 구간) 확인. 유지되면 전량(838 고유, ~1.1시간) 처리 진행.
